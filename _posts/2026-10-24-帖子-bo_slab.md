## 分配思路

本次 `bo_slab` 实现参考 AMD driver 的做法，对 **256 B～2 MiB** 范围内的 BO 使用 slab 子分配。这里记录的是本次实现的范围，具体分配边界、对齐要求和可用属性仍由实现决定。

slab 的思路是先申请一个较大的底层 BO（backing BO），再从里面划出多个小块。上层资源拿到的是其中一个子分配，需要同时记录它所属的 backing BO、块内 offset 和 size。

```text
backing BO：一整块底层分配
├─ slab entry A：offset A + size A → texture A
├─ slab entry B：offset B + size B → texture B
└─ slab entry C：offset C + size C → buffer C
```

这样可以减少小资源各自创建底层 BO 的开销。但 **一个 slab entry 并不等于一个独立的底层 BO**，共享、导出 handle 时必须处理这层差别。

## 遇到的问题：createImageFromTexture 后共享出一个超大 BO

纹理最初创建时，并不一定知道后面会经过 `createImageFromTexture` 进入共享路径，因此原来的存储可能已经分配在 slab 里面。

问题出在共享路径没有识别这层子分配：直接沿用原来的 BO 导出逻辑，shared 返回的实际是整个 backing BO，而不是纹理单独占用的小块。

```text
创建 texture
  → 从 slab 分配一个小块
  → createImageFromTexture，进入共享路径
  → 导出时未处理 slab entry
  → shared 对应整个 backing BO，表现为一个超大 BO
```

这里要区分三个量：纹理实际使用的大小、slab entry 的大小，以及 backing BO 的大小。它们可能不同。即使底层 handle 导出成功，也不能据此判断共享结果正确；还要确认接收方如何解释 offset、大小和布局。

## 处理时机：在 flush_resource 中 move

本次处理方式是在 `flush_resource` 中识别仍位于 slab 的共享资源，将它搬迁到独立 BO，然后再导出这个独立 BO 的 handle。

```text
共享资源仍在 slab 中
  → flush_resource
      → 分配满足共享要求的独立 BO
      → 将资源内容从 slab entry 搬迁到独立 BO
      → 更新 resource 的 BO 引用和相关 offset
      → 处理拷贝与后续访问之间的同步
  → get_handle
      → 导出搬迁后的独立 BO
```

之所以把 move 放在 `flush_resource`，是因为**当前这条 `get_handle` 路径没有可用的 GPU context 来执行搬迁操作**。导出 handle 本身不能替代内容拷贝，也不能自动完成 GPU 命令提交。

`flush_resource` 所在的 context 路径可以安排搬迁及其同步。这里的 flush 也不应简单理解成 CPU 等待 GPU 空闲；关键是保证消费者访问新 BO 前，旧内容的写入和搬迁已经按要求完成。

搬迁时还需要注意：

- 更新资源的 BO 引用、offset，以及依赖原地址的绑定状态。
- 旧 slab entry 必须保留到仍引用它的 GPU 操作完成，才能回收复用。
- 后续对 texture 的访问应使用搬迁后的存储，确保 texture 与共享 image 仍指向同一份资源内容。
- 如果创建时已经明确知道资源需要共享，可以直接使用独立 BO，避免后续搬迁。

## slab 挂在 winsys：设备、screen 与 context 的关系

按这里参考的 AMD driver 结构，slab 管理器挂在设备级 `amdgpu_winsys` 上。它的生命周期和共享范围属于设备层，不属于某一个 `si_context`。

下面是对象关系示意；树的缩进用于表达层级，实际访问还通过指针关联：

```text
amdgpu_device（一个 GPU）
 └─ amdgpu_winsys              设备级，多个 screen 共享
     │                        按 device 去重、引用计数
     │   持有 pb_cache、pb_slabs、BO 全局列表、CS 提交线程队列
     │
     ├─ amdgpu_screen_winsys   每个 screen（每个 fd）一个
     │                        实现 radeon_winsys 接口
     │     ↑ si_screen->ws 指向它提供的接口
     │
     └─ si_screen (pipe_screen)
         └─ si_context (pipe_context) × N
             ├─ 内核 context（amdgpu_ctx，由 ws->ctx_create 创建）
             └─ gfx_cs (radeon_cmdbuf) ≈ amdgpu_cs
                 ├─ amdgpu_cs_context csc1
                 └─ amdgpu_cs_context csc2
```

`amdgpu_winsys` 管理设备范围内的 BO 和 slab，使多个 screen/context 可以复用这些分配设施；`amdgpu_screen_winsys` 提供每个 screen 使用的 winsys 接口；`si_context` 则负责具体的 GPU 操作与命令提交。

因此，**slab 管理器能够找到 backing BO，并不表示它拥有当前资源所需的 GPU 操作上下文**。这也解释了为什么分配管理放在 winsys，而共享前的内容搬迁安排在有 context 的 `flush_resource` 路径。

## 检查共享结果

针对这个问题，应检查以下内容，不能只看 handle 是否导出成功：

1. 共享前记录 resource size、slab entry size、backing BO size 和 offset，确认原资源是否来自 slab。
2. 共享后确认 resource 已切换到独立 BO，导出的是新 BO；其大小满足资源布局和对齐要求，不再是原 slab 的整块 backing BO。
3. 检查共享前写入的内容，以及共享后的读写，确认 texture 与 image 的内容一致。
4. 在 GPU 尚有未完成访问时触发共享，检查搬迁同步和旧 slab entry 的回收时机。
